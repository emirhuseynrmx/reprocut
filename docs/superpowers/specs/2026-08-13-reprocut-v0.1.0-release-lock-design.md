# ReproCut v0.1.0 release-lock design

**Status:** Approved and scope-locked on 2026-08-13

**Release line:** `0.1.0`

**Tag state:** Blocked until every gate in this document passes on one commit

**Architecture decision:** [ADR-001](../../adr/0001-reprocut-server-modular-monolith.md)

## 1. Release promise

ReproCut v0.1.0 accepts a failing project and produces a smaller project only
when the configured failure identity is preserved. The produced bundle is not
merely a runtime record: it binds retained files, the attempt ledger, final
observations, and derived outputs into one independently checkable structure.
A third party can rerun the recorded contract to establish current behavioral
equivalence.

Hashes provide integrity and internal consistency, not authorship. A malicious
party able to replace the entire bundle can construct a new internally
consistent bundle. Authorship or historical execution claims require signed
provenance from the server, CI identity, or a user-provided signing key. The CLI
never describes unsigned, non-rerun evidence as proof of who executed it.

The self-hosted server applies the same contract to GitHub and GitLab jobs. It
may automate a reduction, but it cannot weaken the CLI's oracle, evidence, or
publication invariants.

The final `v0.1.0` tag, crates.io publication, PyPI publication, GitHub Release,
and server image are forbidden until the exact tagged commit satisfies this
document. A skipped, cancelled, missing, stale, or differently committed gate
is a failure.

## 2. Locked product scope

v0.1.0 includes:

- project-level, manifest-aware, and syntax-aware reduction;
- automatic, regex, and exit-zero failure oracles;
- Rust/Python normalization and fingerprint parity;
- immutable metadata-aware snapshots and resumable search;
- independently verifiable evidence bundles;
- HTML and issue reports, reproducibility script, OCI export, and gallery
  preparation behind verification gates;
- Rust CLI, typed Python client/native binding, and editor protocol;
- explicit privacy/redaction controls;
- global reduction budgets and lockfile policy;
- a single-node self-hosted ReproCut Server;
- GitHub App and GitLab webhook/provider adapters;
- a durable SQLite queue, content-addressed artifacts, isolated workers,
  lease fencing, and idempotent publication reconciliation.

v0.1.0 does not include:

- a hosted multi-tenant "ReproCut Cloud";
- Postgres, Kubernetes, distributed scheduling, billing, or organization-wide
  analytics;
- arbitrary online dependency installation;
- implicit shell evaluation or repository-controlled execution policy;
- LLM-based failure classification;
- a promise that every Poetry, PDM, Hatch, npm workspace, or target-specific
  Cargo extension can be structurally reduced.

Those exclusions are scope boundaries, not silent fallbacks. Unsupported input
fails early or remains conservatively retained.

## 3. Versioned contracts

The final release uses one authoritative version table shared by Rust, Python,
protocol validation, generated documentation, demo generation, and the static
release audit.

| Contract | v0.1.0 version |
| --- | ---: |
| Normalization | 5 |
| Reduction evidence | 4 |
| Resume/session contract | 3 |
| CI evidence | 1 |
| Artifact manifest | 1 |
| Server database | 1 |

An older normalization, evidence, or session contract is incompatible. It is
never silently migrated, interpreted as current evidence, or reused for a
candidate cache decision. User-facing text always names the contract instead
of using the ambiguous word "schema" alone.

## 4. Correctness kernel

### 4.1 Normalization schema 5

Normalization is contextual and conservative. A value is volatile only when a
closed rule identifies its diagnostic role. False negatives are preferred to
erasing a semantic discriminator.

UUIDs are normalized only in recognized metadata fields such as request,
correlation, trace, span, invocation, or run identifiers. A UUID in an
assertion, exception message, entity key, or other unqualified semantic text is
preserved.

Timestamps are normalized only in a recognized log envelope or explicit log
metadata field. A timestamp in expected/actual values, validation messages,
deadlines, or domain data is preserved.

Durations are normalized only in execution telemetry contexts such as
`elapsed`, `took`, `duration`, or `finished in`. Timeout, deadline, retry,
expected, actual, and unqualified duration values are preserved.

Source locations require stack/compiler/test-location context. URL schemes and
root-relative routes are never source locations. Data/manifest suffixes such
as `.json`, `.yaml`, `.yml`, and `.toml` are not sufficient evidence by
themselves. Explicit compiler arrows, stack frames, `File ..., line ...`, and
recognized source-file locations may normalize line/column values.

The shared Rust/Python adversarial corpus includes at least:

| Baseline change | Expected verdict |
| --- | --- |
| semantic UUID changes | rejected |
| request/correlation UUID changes | preserved |
| semantic timestamp changes | rejected |
| log-envelope timestamp changes | preserved |
| `timeout 10ms` becomes `timeout 20ms` | rejected |
| `elapsed 10ms` becomes `elapsed 20ms` | preserved |
| `error.json:404` becomes `error.json:500` | rejected |
| `/api/error.json:404` becomes `:500` | rejected |
| URL status `:404` becomes `:500` | rejected |
| `src/main.rs:12` becomes `src/main.rs:99` | preserved |

Every corpus item asserts normalized text, anchors, fingerprint digest, stream
ownership, and verdict parity in the Rust implementation, Python fallback, and
native Python wheel.

### 4.2 Oracle invariants

- Automatic mode requires stable, discriminative anchors. Termination alone,
  punctuation, generic summaries, and location-only frames cannot authorize a
  cut.
- `combined` reserves at least one eligible anchor from each stream before
  filling the remaining anchor budget.
- Regex mode matches bounded canonical-newline diagnostic bytes and never
  erases semantic numbers before matching.
- Exit-zero mode activates only explicitly.
- Timeout, truncation where output is evidence, runner failure, incomplete
  capture, invalid configuration, and ambiguous baseline are inconclusive or
  fatal. None is `Preserved`.
- Only `Preserved` can authorize a transition.
- Final verification uses the same resolved contract and records every
  observation, not only an aggregate count.

### 4.3 Baseline before durable cache

The engine order is fixed:

1. resolve inventory and state/output exclusions;
2. capture a stable source snapshot;
3. resolve preparation and execution identities;
4. run and stabilize baselines;
5. construct the actual failure fingerprint;
6. construct session contract v3;
7. open or create the state journal;
8. search, verify, and publish.

The same source, argv, and automatic oracle specification with a different
actual baseline failure is a different session. No old candidate verdict is
consulted before this distinction is known.

## 5. Stable snapshots and filesystem contract

### 5.1 Capture protocol

Snapshot capture is a bounded, two-pass stability protocol:

1. enumerate entries in canonical order;
2. for each entry, compare metadata before and after reading and capture its
   bytes/target/metadata;
3. perform a second complete enumeration and content/metadata pass;
4. require identical paths, entry kinds, sizes, executable masks, identities
   where the platform exposes them, and content digests;
5. fail with `SourceDrift` after the bounded retry budget rather than accepting
   a mixed-time snapshot.

Files are opened without following a newly substituted symlink. The engine
never rereads candidate bytes from the live checkout after capture.

### 5.2 Represented entries

The canonical snapshot represents:

- regular files and their Unix owner/group/other executable mask;
- empty directories;
- relative symlinks whose normalized target remains inside the snapshot root.

Absolute, escaping, cyclic, or platform-unrepresentable symlinks are rejected.
Non-UTF-8 Unix paths and unpaired Windows UTF-16 paths are rejected early with
an explicit compatibility error in v0.1.0; lossy conversion is never used for
identity. Valid OS strings are encoded with a platform tag and native units in
digests.

`.git` is excluded whether it is a file or directory. A custom state database
or output path inside the source root is excluded before capture; ambiguous
overlap with a reducible entry is rejected. Generated and dependency-directory
exclusions apply to every matching path segment, not only the root.

### 5.3 Lockfiles

Lockfiles are protected by default. `--allow-lockfile-removal` is the explicit
opt-in for reducing them. The policy and protected path set are part of the
session contract and evidence.

### 5.4 Ecosystem adapter coverage

The common static shapes below are first-class v0.1.0 contracts:

- Cargo root/workspace dependencies, target-specific dependency tables,
  features, members/excludes, explicit targets, and lockfile protection;
- PEP 621 dependencies, optional groups, scripts, and entry points; Poetry
  dependency/group/extras/script tables; PDM dependency, optional, development,
  and script tables; and statically declared Hatch environment dependencies;
- npm dependencies/dev/peer/optional maps, scripts, bin entries, and workspace
  array or `{ packages = [...] }` forms.

Unknown keys are preserved. Dynamic dependency generation, plugins, inherited
external configuration, and package-manager expressions ReproCut cannot model
are reported and retained rather than rewritten speculatively. Every supported
shape has golden round-trip, comment/format preservation, and real-tool parse
tests.

## 6. Session contract and candidate cache v3

The session digest length-delimits and binds:

- source snapshot digest;
- actual failure fingerprint digest;
- exact command argv using non-lossy OS-string encoding;
- oracle mode, channel, policy, patterns, and normalization schema;
- preparation contract and frozen dependency source;
- inventory, symlink, lockfile, and redaction policies;
- timeout, output, deadline, attempt, preparation, and concurrency budgets;
- environment policy and environment digest;
- resolved program identity and preparation-tool identities;
- engine/build identity and platform.

Program/tool identity includes canonical resolved path, bounded version-output
digest, and executable digest. Known execution-affecting environment variables
are bound by default; users can add names with `--bind-env`. Values are hashed,
not copied into public evidence. Secret-looking names and values are absent
from reports.

Every attempt, transition, and candidate cache record carries the actual
failure fingerprint digest. Structured candidates also carry the realized
prepared-snapshot digest. On a cache lookup, ReproCut realizes the candidate
again; a digest mismatch becomes a cache miss and a real oracle execution.

## 7. Evidence schema 4 and `reprocut verify`

### 7.1 Non-circular evidence envelope

Evidence is finalized in two layers to avoid a hash cycle:

1. `EvidencePayload` contains the reduction/session identity, retained snapshot
   manifest, attempts, measurements, and final verification observations.
2. Reports are generated from the canonical payload and embed its digest.
3. `reduction.json` wraps the payload, payload digest, and hashes of derived
   report/issue outputs.
4. The canonical payload inside `artifact-manifest.json` binds
   `reduction.json`, `attempts.jsonl`, the retained project manifest, reports,
   reproduction files, and their sizes/digests. The manifest envelope itself
   is excluded from its member list and stores the calculated root identity.

The root artifact identity is:

```text
artifact_id = sha256(canonical artifact-manifest payload)
```

The retained manifest records every relative path, entry kind, byte digest,
size, and executable mask or symlink target. A one-byte or metadata change
invalidates the existing artifact. Re-authoring a complete replacement is
detectable as a new artifact identity and, when provenance is present, a
signature/provenance mismatch.

The source snapshot identity is recomputed from its canonical embedded source
manifest. Source bytes are verified as well only when an explicit
`--include-source` bundle contains them; otherwise the verifier reports source
identity as recorded-manifest integrity rather than claiming possession of the
original bytes.

### 7.2 Verification command

`reprocut verify OUTPUT` independently checks:

- schema versions and canonical encodings;
- source and retained snapshot identities;
- exact entry set, bytes, sizes, kinds, targets, and executable masks;
- attempt-ledger equality, unique monotonic IDs, event ordering, verdicts,
  candidate identities, and transition arithmetic;
- oracle-spec, failure-fingerprint, preparation, environment, and session
  digests;
- measurements and accepted-size monotonicity;
- individual final-verification observations;
- derived report/issue hashes and embedded payload identity;
- artifact-manifest identity and absence of undeclared files other than its
  defined envelope.

`--rerun N` optionally executes the recorded resolved contract in a fresh
workspace and requires `N/N` matching observations. Structural verification is
always offline; rerun follows the captured network/preparation policy.

The type-level publication boundary is `VerifiedArtifact`. OCI export, gallery
preparation, PR/MR publication, completion, and any public artifact API accept
only that type. A modified artifact fails with a specific integrity error.

### 7.3 Privacy and redaction

Artifacts use project-relative paths and never need the caller's absolute
source, state, or output path. Diagnostics and argv can still contain private
data, so the CLI warns against secrets in command-line arguments.

`--redact-paths` and `--redact-command` define the original artifact policy.
`reprocut redact OUTPUT --to SHARE_OUTPUT` creates a `VerifiedShareBundle`, not
a `VerifiedArtifact`; it never mutates the parent. The share bundle records its
parent artifact digest and explicitly marks capabilities such as rerun or OCI
export that redaction removed.

## 8. Publication and OCI integrity

Output publication uses an operating-system no-replace primitive. A platform
without a safe atomic primitive fails closed; it does not claim no-clobber.
Temporary output is flushed, files are synced, the directory is committed, and
the parent directory is synced where supported before success is reported.

OCI runtime bases must resolve to `name@sha256:digest`. The resolved base digest
is evidence. Archive verification parses and validates the complete
index-manifest-config-layer descriptor chain, media types, sizes, digests, path
safety, and required ReproCut labels. Mutable tag-only bases cannot produce a
publishable v0.1.0 artifact.

OCI archives, gallery entries, and redacted bundles are derivative artifacts.
Each has its own canonical manifest and identity and binds the parent
`artifact_id`; none is inserted back into the parent manifest. This prevents
identity cycles while retaining a verifiable chain of custody.

## 9. Budgets and validation

Every surface validates the same typed request before emitting `Started`:

- per-attempt timeout and output cap are positive;
- jobs/concurrency is within its allowed range;
- ecosystem and preparation mode are supported together;
- total deadline, CPU-time allowance where the platform exposes enforceable
  accounting, maximum attempts, maximum preparations, total captured output,
  and retained disk budget are positive and bounded;
- paths, symlink policy, lockfile policy, and oracle combinations are valid.

Exhausting a global budget produces a durable, non-publishable terminal reason.
The CLI, JSON protocol, Python client, editor extension, and server all consume
the same contract validation fixtures.

`BaselineStable` is emitted immediately after stabilization and before search
progress. It cannot be synthesized after reduction completes.

## 10. ReproCut Server

### 10.1 Architecture

The server is a modular monolith:

```text
GitHub/GitLab webhook
    -> authenticated delivery journal
    -> durable SQLite job queue
    -> fenced isolated worker
    -> ReproCut correctness kernel
    -> VerifiedArtifact
    -> publication outbox/reconciliation
    -> PR/MR result
```

Production support in v0.1.0 is Linux on one host with the database and WAL on
local storage. The interfaces permit later Postgres/object-storage/container
orchestration implementations, but no distributed claim is made.

The server binary is packaged as `reprocut-server` at version `0.1.0`. The
Python distribution remains a client/native-binding package and does not embed
the server.

### 10.2 Trust types

The domain separates:

```rust,ignore
UntrustedJobIntent
TrustedExecutionPolicy
ResolvedJobContract
UnverifiedArtifact
VerifiedArtifact
```

Webhook or repository data cannot directly construct a trusted policy or
resolved contract. `ResolvedJobContract` requires an authenticated intent,
server-controlled policy, exact checkout, stabilized failure, and resolved
environment/tool identities.

Execution policy comes from server administration or a trusted default/base
revision. Fork/PR content cannot enable network, select a privileged image,
raise budgets, add host mounts, change secrets, or replace the failure command.

### 10.3 Separate state machines

Webhook delivery:

```text
received -> authenticated -> accepted -> dispatched
                    \-> rejected
                         duplicate
```

Reduction job:

```text
queued -> leased -> resolving -> baseline -> reducing -> verifying
       -> verified -> publishing -> completed
       \-> failed | cancelled | expired
```

Publish outbox:

```text
pending -> sending -> reconciled -> delivered
                \-> retryable -> pending
                     dead_letter
```

These are distinct tables/types, not one status enum.

### 10.4 SQLite durability and leases

The server enables WAL, `synchronous=FULL`, foreign keys, busy timeout, bounded
connections, and controlled checkpointing. WAL is forbidden on a network
filesystem. Startup asserts bundled SQLite `>= 3.51.3`; the dependency must
also compile with the workspace's Rust 1.85 MSRV. The current SQLite 3.49.1
binding is therefore a release blocker.

Claims use a write transaction and compare-and-swap. Every successful claim
increments a monotonic fencing token. A heartbeat extends only the matching
`job_id + lease_owner + fencing_token` lease.

All worker-authorized mutations, including state transitions, verification
records, artifact promotion, outbox enqueue, and final completion, require the
same live ownership tuple. A stale worker may finish computation but cannot
make it visible.

### 10.5 Artifact store

Workers write only to:

```text
tmp/<job-id>/<fencing-token>/...
```

After verification, the control plane rechecks the live fence and atomically
promotes content into:

```text
artifacts/sha256/<first-two-hex>/<artifact-id>
```

Promotion verifies bytes, syncs data, and is idempotent. Reads execute full
structural verification of the manifest and every declared member before
returning `VerifiedArtifact`; checking only the root manifest digest is
insufficient. Database paths never serve as integrity authority.

### 10.6 Worker isolation

Production workers require a rootless OCI backend with:

- read-only base image and fresh bounded workspace;
- no Docker socket, privileged mode, host PID namespace, or arbitrary host
  mount;
- minimal short-lived credentials during exact-revision fetch only;
- network disabled after fetch;
- CPU, memory, PID, disk, wall-clock, output, attempt, and preparation limits;
- process-tree kill/reap and workspace removal on every exit path.

Exact-revision checkout disables repository/system hooks, interactive
credential helpers, submodule recursion unless trusted policy enables it, and
repository-controlled Git configuration. Credentials are scoped to the fetch
process and removed before preparation or execution.

The process backend is development-only and requires the explicit
`--allow-unsafe-process-worker` flag. Server startup refuses that flag in the
production profile.

### 10.7 Provider security and idempotency

GitHub signatures are verified over the untouched raw body with HMAC-SHA256
and constant-time comparison. GitLab signed webhook verification validates the
standard signature/timestamp/replay contract; legacy token comparison is an
explicit compatibility mode. Invalid payloads never create work.

Deliveries are unique by provider and provider delivery ID. The logical intent
identity binds provider, repository identity, target revision, trusted policy
digest, and requested command identity. The resolved-contract identity is a
second digest created only after baseline and environment resolution.

GitHub installation tokens are generated on demand and retained only in
memory. Provider hosts and repository identities are allowlisted to prevent
credential forwarding and SSRF.

External comment APIs cannot offer exactly-once delivery. Publication therefore
uses a transactional outbox, deterministic hidden result marker, lookup, and
upsert/reconciliation. A crash after remote success but before local commit
updates the same comment instead of creating a duplicate.

Provider-specific concepts stop at adapters:

```rust,ignore
trait SourceProvider { /* resolve and checkout exact revisions */ }
trait ChangeRequestPublisher { /* find and upsert results */ }
trait JobStore { /* durable state and fenced transitions */ }
trait ArtifactStore { /* staged and verified content */ }
trait WorkerBackend { /* isolated execution */ }
```

## 11. CI evidence and supply chain

Every GitHub Action reference is pinned to a full commit SHA. Miri and
sanitizer jobs use dated toolchains; runner, compiler, Cargo, Python, Node,
container runtime, SQLite, and action identities are recorded.

Each matrix cell emits a gate record containing logical gate name, workflow
path/digest, run ID, run attempt, head SHA, job ID/name, matrix values,
conclusion, completion time, and output digests. A final `release-evidence` job
runs with `if: always()`, knows the expected matrix cardinality, rejects missing
or non-success cells, and produces CI evidence schema 1.

The release collector independently queries the GitHub API for the exact run
and reconciles the records with actual job conclusions. The release workflow
requires the evidence head SHA to equal the peeled signed tag commit. Evidence
from another run, attempt, workflow revision, or commit is invalid.

All Cargo/Maturin graph operations use the committed lockfile and `--locked`.
Packages and images include SBOMs, checksums, and provenance bound to the same
commit.

## 12. Test and fault-injection matrix

Implementation is test-driven. In addition to existing unit, property, parity,
Loom, Miri, sanitizer, package, and cross-platform tests, v0.1.0 proves:

- contextual UUID/timestamp/duration and route/URL adversarial cases;
- one-byte, permission, symlink-target, extra-file, and missing-file tampering;
- attempt/event/report/artifact-manifest tampering;
- a changed baseline failure cannot resume old state;
- changed env/tool/binary/prepared snapshot cannot reuse a cached verdict;
- drift during either snapshot pass fails closed;
- concurrent atomic no-replace publication has one winner;
- mutable OCI bases and broken descriptor chains are rejected;
- global budget exhaustion cannot publish;
- webhook retries, duplicates, reordering, invalid signatures, and replays;
- two workers racing for one job;
- worker death after claim and stale wake after lease expiry;
- crash after artifact write but before promotion;
- crash after remote comment success but before local commit;
- server death during every durable transition;
- database process termination mid-transaction and disk-full during sync;
- verification success followed by artifact mutation;
- malicious fork attempts network access, fork bomb, host mount, `/proc` access,
  policy override, or secret exfiltration.

For every injected crash, the visible result is either the complete prior state
or the complete next state. No partial artifact or unauthorized transition is
publishable.

## 13. Final release gate

The final tag requires all of the following on one clean commit:

1. format, Clippy `-D warnings`, workspace/all-target tests, and docs under
   Rust 1.85 with the committed lockfile;
2. Rust/Python/native-wheel parity and Python 3.9-3.13 tests;
3. Linux, Windows, and macOS CLI/integration tests;
4. Loom, Miri, sanitizer, supply-chain, OCI, editor, gallery, server, provider,
   isolation, crash-recovery, and package gates;
5. exact-commit CI evidence with every expected matrix cell successful;
6. regenerated demo whose source, retained project, measurements, ledger,
   reports, and artifact identity pass `reprocut verify`;
7. release-smoke output passing structural verification and fresh rerun;
8. crates.io `cargo package` and `cargo publish --dry-run --locked` for every
   public crate, including `reprocut-server`;
9. Maturin wheel/sdist builds, `twine check`, and clean-install smoke tests;
10. six native archives, server OCI archive, SBOMs, checksums, and provenance;
11. a static audit that detects stale docs, schema numbers, mutable action
    refs, mutable OCI bases, local-machine archaeology, and unbound evidence;
12. a clean tracked tree except explicitly ignored build output.

After those gates pass, the user performs the irreversible actions: create the
signed immutable tag, approve protected release/registry environments, publish
crates.io packages in dependency order, publish PyPI through trusted
publishing, and verify clean public installs. Tokens and registry publication
remain user-controlled.

## 14. Locked implementation order

1. normalization/oracle schema 5 and shared adversarial parity;
2. evidence schema 4, artifact manifest, and `reprocut verify`;
3. session/cache v3 and baseline-before-state orchestration;
4. snapshot, filesystem, privacy, OCI, budgets, publication, and protocol
   hardening;
5. demo regeneration, schema-doc synchronization, and exact CI evidence;
6. server domain/state/artifact foundations;
7. fenced rootless worker;
8. GitHub App adapter and reconciled publication;
9. GitLab adapter and compatibility modes;
10. full fault injection, release audit, packaging, and immutable release proof.

Later phases cannot weaken an earlier invariant. Server work starts only after
the standalone CLI can produce and independently verify a trustworthy bundle.

## 15. Definition of locked

This document is the v0.1.0 scope authority. New features are deferred unless
they are necessary to satisfy one of its invariants. A discovered correctness,
security, evidence-integrity, or release-reproducibility defect is not a feature
and remains eligible for v0.1.0.

No claim of a final, verified, reproducible, publishable, or registry-ready
v0.1.0 is valid until Section 13 passes on the exact release commit.
